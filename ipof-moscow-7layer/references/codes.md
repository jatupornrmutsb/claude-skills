# ระบบรหัสและทะเบียนข้อกำหนด

## 1. รหัส

| รหัส | ความหมาย | หมายเหตุ |
|---|---|---|
| P01… | ปัญหา | 5–8 ข้อ จากแบบสอบถาม |
| N01… | ความต้องการ | 10–15 ข้อ แบ่ง ด้านข้อมูล / ด้านหน้าที่ของระบบ / ด้านคุณภาพ |
| FR01… | ข้อกำหนดเชิงหน้าที่ | สิ่งที่ระบบต้องทำ รวมการจัดเก็บข้อมูล |
| NFR01… | ข้อกำหนดที่ไม่ใช่หน้าที่ | คุณภาพหรือเงื่อนไขของระบบ |
| CON01… | ข้อจำกัด | จากคำตอบปลายเปิดและข้อเสนอแนะผู้เชี่ยวชาญ |
| OP01… | คำถามปลายเปิด | |
| TC-01… | กรณีทดสอบ | ในตารางตรวจสอบย้อนกลับ |
| G1–G4 | กลุ่มหน้าที่ของ FR | NFR ไม่จัดกลุ่ม |
| L1–L7 | ชั้นสถาปัตยกรรม | |

เลขเรียงต่อเนื่อง ไม่ใช้ซ้ำ ไม่ข้าม รหัสเดียวกันใช้ความหมายเดียวกันทุกไฟล์

## 2. กลุ่มหน้าที่ (จำแนก FR ตามคำกริยาหลัก)

| กลุ่ม | ชื่อ | คำกริยา | ชั้นหลัก |
|---|---|---|---|
| G1 | จัดการข้อมูล | จัดเก็บ บันทึก | L5 |
| G2 | ประมวลผล | คำนวณ จัดลำดับ เปรียบเทียบ | L4 |
| G3 | สืบค้นและคัดเลือก | ค้นหา เชื่อมโยง | L3 |
| G4 | นำเสนอและสื่อสาร | แสดงผล สร้างรายงาน แจ้งเตือน | L2 |

NFR อยู่ใน L2 (การใช้งาน/การแสดงผล), L6 (สิทธิ์ ความปลอดภัย ที่มา ประวัติ), L7 (ความทันเวลา การเชื่อมต่อ ความพร้อมใช้) ตามลักษณะ

## 3. การสังเคราะห์ N → ข้อกำหนด

- รวม N ที่ใช้ข้อมูลเดียวกันหรือทำหน้าที่เดียวกันเป็นข้อเดียว (หลาย N ต่อ 1 ข้อกำหนด) และบันทึกใน `needs` ว่ามาจาก N ใด พร้อม `reason`
- เป้าหมาย ≤ 15–20 ข้อ และ Must ≤ 6–8 ข้อ
- **ห้ามรวมจนกว้างเกินกว่าจะเขียนเกณฑ์ยอมรับได้** — ถ้าเขียนเกณฑ์เชิงปริมาณข้อเดียวไม่ได้ ให้แยก
- ความเชื่อมโยง P–N–ข้อกำหนดเขียนพร้อมเหตุผล NFR ที่ไม่ผูกกับปัญหาเฉพาะใช้ "–"
- ทุก N ต้องถูกสังเคราะห์ หรือมีเหตุผลที่ไม่นำไปเป็นข้อกำหนด

## 4. แบบประโยคข้อ Must (หลังยืนยันครั้งที่ 1)

ชื่อระบบ + สิ่งที่ระบบต้องตอบสนอง (บรรยายเป็นประโยคปกติ ไม่ใส่เครื่องหมายคำพูด) แล้วกำหนด

- เกณฑ์ยอมรับเชิงปริมาณ (ตัวเลข หน่วย เงื่อนไข เช่น "ภายใน 1 นาทีหลังตรวจพบ ในร้อยละ 95 ของเหตุการณ์ทดสอบ")
- วิธีตรวจสอบ: Test, Analysis, Inspection หรือ Demonstration
- กรณีทดสอบ TC-xx

## 5. ทะเบียน `project.json`

ฟิลด์ของข้อกำหนด: `code, type, group, text, short, needs[], problems[], reason, data_type, moscow_score, moscow_final, moscow_reason, layer, component, flow_stage, ipof{part,sub}, acceptance, verification, tc[], depends_on[], added_after_eval`

`python scripts/analyze.py validate --project project.json` ตรวจรูปแบบรหัส การอ้างข้าม กลุ่ม/ชั้น เหตุผลของระดับที่ต่าง Must ที่พึ่งพาข้อไม่ใช่ Must และองค์ประกอบของ Must
